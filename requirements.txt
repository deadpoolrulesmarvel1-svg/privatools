# Runtime dependencies. Every package is pinned to an exact version so a
# rebuild is reproducible and CVE exposure can't drift silently between builds
# (research DEP1). The versions below match what is running in production
# (captured from `pip freeze` in the deployed image), so pinning is a no-op for
# behaviour — it just freezes the known-good set. All have manylinux wheels for
# both linux/arm64 and linux/amd64 at these versions, so the multi-arch release
# build is unaffected.
#
# This file is the human-edited SOURCE of runtime deps (direct, pinned). The
# Docker image and PR CI install from the generated, fully-hashed transitive
# lockfile `requirements.lock` with `--require-hashes` (integrity — DEP1/DEP4).
#
# EDITING THIS FILE ALONE HAS NO EFFECT — the image installs from the lock, so a
# bump here that isn't compiled into the lock silently never reaches production.
# `backend/tests/test_requirements_lock_sync.py` fails the build if the two drift.
# (This is why every Dependabot pip PR must be closed rather than merged: it
# edits this file and never regenerates the lock.)
#
# Regenerate on the PROD VM, not a laptop — the lock must resolve for
# linux/aarch64, and uv otherwise mis-resolves numba/llvmlite for py3.10:
#
#   # 1. constraints from the RUNNING container, minus whatever you are bumping
#   docker exec privatools-privatools-1 pip freeze > prod-freeze.txt
#   grep -vE '^(pkg-you-are-bumping)==' prod-freeze.txt > constraints.txt
#
#   # 2. compile both locks against it
#   uv pip compile requirements.txt     -c constraints.txt --generate-hashes \
#       --universal --python-version 3.10 -o requirements.lock
#   uv pip compile requirements-dev.txt -c constraints.txt --generate-hashes \
#       --universal --python-version 3.10 -o requirements-dev.lock
#
#   # 3. prove it installs before committing
#   pip install --dry-run --require-hashes -r requirements.lock

# Clerk session verification. Clerk signs its session tokens RS256, so checking
# one needs RSA — which the standard library does not have. PyJWT does the JWT
# work and cryptography does the maths.
#
# Declared together on purpose: pyjwt[crypto] would pull cryptography in as an
# extra, and app/auth/clerk_session.py imports cryptography's exceptions
# directly, so test_declared_dependencies would (rightly) object to it arriving
# as somebody else's transitive dependency.
#
# The alternative was asking Clerk's API to verify each token, which would put
# a network round-trip on every key request and make API key management stop
# working whenever Clerk had an incident.
pyjwt==2.13.0
